## N160: 对话上下文预算管理（E2E 逐次试错 + 工具输出未过滤）

> **级别**: L1 可复用经验（Y/N 检查清单 + 影响 AI 全局行为）
> **分类**: 工作流约束 — 对话上下文管理
> **来源**: 2026-07-14 用户反馈"我说的是对话咋莫名其妙断了，又要新开" + "为什么不多分配子agent呢"
> **状态**: ✅ FIXED（§4.10 新增 4 条硬约束 + 索引 N160）

### 触发原话

> "我说的是对话咋莫名其妙断了，又要新开"
> "为什么不多分配子agent呢，有经验需要沉淀吗？"

### 症状

S3 阶段（10 文件 +1089/-292 行 diff）执行中，Trae IDE 对话频繁强制重置/压缩，用户需反复新开对话。根因是主对话上下文消耗过快：

1. **E2E 调试逐次试错**：Select selector 找不到 → 改 1 个重跑 1 次 → 再改再跑，3 轮 E2E 调试每轮消耗 5000+ token（Playwright 启动 + 截图 + 错误堆栈）
2. **pytest -v 输出未过滤**：69 个测试名 + PASSED 标记全部进上下文，约 2000 token；git log/netstat 等也全量进上下文
3. **大文件整文件 Read**：LogAnalysisPanel.tsx 680 行全量读取，实际只需 29-180 段
4. **未用子 agent 分发**：全部代码细节读进主上下文，而 S3 子任务高度可并行（RAG 接入 / Celery 异步化 / 前端轮询 / 测试）

### 根因分析

- **直接原因**：工具输出未过滤 + 大文件全量读取 + E2E 逐次试错
- **根本原因**：未遵循 N159（长任务分子 agent），全部工作在主上下文执行
- **架构层面**：§4.10 Spec 分阶段只约束了"单阶段 diff < 1500 行"，未约束"单阶段对话上下文消耗"

### 修复方案

§4.10 新增 4 条硬约束 + 1 条禁止项（commit `-`）：

#### 1. 工具输出过滤
- `pytest` 用 `-q --tb=short` 非 `-v`
- `git log` 用 `--oneline -N`（N ≤ 10）
- Grep 用 `head_limit` 参数限制输出行数
- 长输出用 PowerShell `Select-Object -First N`

#### 2. E2E 调试 ≤ 2 轮
- 首次失败 → 写诊断脚本一次性 dump 全部 DOM 结构 + 元素计数 + bbox
- 根据诊断结果针对性修复
- 禁止"改 1 个 selector 重跑 1 次"的逐次试错

#### 3. 大文件精确读取
- 用 `offset`+`limit` 精确读取目标段落
- 禁止整文件 Read（除非文件 < 100 行）

#### 4. 主动提示新开对话
- 单阶段对话轮次 ≥ 15 轮时
- 感觉上下文接近饱和时（大量工具输出堆积）
- 主动提示用户："建议本阶段 commit 后新开对话续接下一阶段"

#### 根本解法：N159 子 agent 分发
- 独立子任务分发子 agent（代码细节隔离到子上下文）
- 主 agent 只做：协调 + 定义 API 契约 + commit + 验证
- 并行分发用单条消息多个 Task 工具调用

### Y/N 检查清单

- [ ] pytest 命令是否用了 `-q` 而非 `-v`？
- [ ] E2E 调试是否 ≤ 2 轮（诊断脚本一次性 dump）？
- [ ] 大文件读取是否用了 `offset`+`limit`？
- [ ] 对话轮次是否 ≥ 15 轮？是 → 提示新开对话
- [ ] 独立子任务是否已分发子 agent（N159）？

- N## 索引表已新增 N160 行
- 本 lesson 文件已创建

## N162: AI 命令防错反思 + spec 范围外关注 + 验证完整性

> **级别**: L1 可复用经验（Y/N 检查清单 + 影响 AI 全局行为）
> **分类**: AI 行为约束 — 命令反思 + 完整性边界
> **来源**: 2026-07-14 用户反馈"ai用某个命令后，要是这个命令是错的，或者要人为确认的，需要在下一步思考为什么会用这个，是不是有更好的替代，下次怎么不继续防错，这都需要沉淀吧" + "spec 范围外的架构问题，在spec中也要关注"
> **状态**: ✅ FIXED（本 lesson + spec 补"范围外关注"段）

### 触发原话

> "补完完把，这种以后都要补完，spec 范围外的架构问题，在spec中也要关注，ai用某个命令后，要是这个命令是错的，或者要人为确认的，需要在下一步思考为什么会用这个，是不是有更好的替代，下次怎么不继续防错，这都需要沉淀吧"

### 症状

#### 反模式 1：AI 用错命令不反思
S3-S6 执行中，AI 多次用错命令或用了需人为确认的命令，但未在下一步反思根因：
- `pytest -v`（应为 `-q`，N160 已沉淀但属事后补，非当时反思）
- PowerShell `&&` 链式（PS 5.1 不支持，应预判）
- `git add . && git commit`（N153 stash 丢失风险，应分步）
- `conda run -n gaf python -c "多行"`（不支持，应写临时文件）

每次用错后，AI 只是当场改对，未反思"为什么用错？是否有替代？下次如何防错？"

#### 反模式 2：spec 范围外问题被忽略
AI 架构缺陷 spec 列了 12 项问题（P0-1~P2-7），执行中发现 3 项范围外问题：
- LangGraph V1.0 弃用警告（`create_react_agent` → `create_agent`）
- Celery worker 未实测 auto_index_rag 真实执行
- RAG ChromaDB 索引检索效果未验证

AI 标"spec 12 项全部 ✅"时未提及这 3 项范围外问题，让用户误以为"AI 架构全部修复完成"。违反 N126 诚实标记 — "全部修复"应包含范围外发现。

### 根因分析

- **反模式 1 根因**：AI 将"命令用错"视为一次性事件，未建立"用错→反思→防错"的反馈循环。N134 反思清单只覆盖 commit 后 4 问，未覆盖"命令使用错误"这个维度。
- **反模式 2 根因**：spec 只列已知问题，未要求"执行中发现的新问题必须追加到 spec 关注段"。AI 严格按 spec 12 项执行，忽略了执行过程本身是发现新问题的机会。

### 修复方案

#### Y/N 检查清单（每次命令用错或需人为确认后必跑）

- [ ] **根因反思**：为什么会用这个命令？是记忆错误？规则未读？还是命令本身有陷阱？
- [ ] **替代方案**：是否有更好的替代命令？是否需要写脚本而非单行命令？
- [ ] **防错机制**：下次如何避免？是否需要加入 lesson？是否需要更新规则文档？
- [ ] **同类扫描**：同类错误是否在其他地方也存在？（如 PS `&&` 问题是否在多个脚本中）

#### spec 范围外关注规则

spec 文件必须包含"范围外关注"段，记录执行中发现的新问题：

```markdown
## 范围外关注（执行中发现）

> 本段记录 spec 执行过程中发现的、不在原 12 项清单内但需关注的架构问题。

| 发现时间 | 问题描述 | 来源 | 处理建议 | 登记到 |
|----------|---------|------|---------|--------|
| 2026-07-14 | LangGraph V1.0 弃用 | S3 执行 | 升级到 create_agent | tech-debt/active.md |
| ... | ... | ... | ... | ... |
```

**硬约束**：
- ✅ spec 执行中发现范围外问题 → 立即追加到"范围外关注"段
- ✅ 范围外问题登记到 `docs/archive/active-tech-debt.md`（如属代码债）或 lessons/（如属经验）
- ✅ 标"spec 全部完成"时必须同时报告"范围外关注"段的问题
- ❌ 禁止只修 spec 内清单就标"全部完成"而不提范围外发现

#### 验证完整性规则

标"阶段 ✅"前必须完成 3 项验证（N128 扩展）：
1. **单元测试**：相关 app tests 全部通过（非只跑新增测试）
2. **全量回归**：受影响 app 的全量测试通过（非只跑单 app）
3. **E2E 验证**（有前端改动的阶段）：Playwright 浏览器实测，0 console errors

**禁止**：
- ❌ 标 ✅ 但 E2E 未做（如 S4/S5/S6 前端未 E2E 验证）
- ❌ 标 ✅ 但 vitest 全量未跑（只跑单文件）
- ❌ 标 ✅ 但后端只跑单 app（未跑全 app 回归）

### Y/N 检查清单（每次标"阶段 ✅"前必跑）

- [ ] 单元测试：相关 app tests 全通过？
- [ ] 全量回归：受影响 app 全量测试通过？
- [ ] E2E 验证：有前端改动的阶段是否 Playwright 实测？
- [ ] 范围外问题：执行中是否发现 spec 清单外的问题？是 → 追加到"范围外关注"段
- [ ] 诚实报告：标"全部完成"时是否同时报告范围外问题 + 未完成验证？
