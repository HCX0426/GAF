# N167 — 代码重构/大规模修改 7 维度评估清单

## 触发原话（用户反馈）

> "代码重构/大规模修改评估维度（线上业务服务完整版，可直接粘贴至规则文档）" — 7 个维度定义
> "这个要沉淀到文档里吧，代码、规则文档和 skill 文档的修改也可以参考这些维度吧"

## 根因

现有 §2.0.5 修改四维度评估原则（2026-07-13）只有 4 个维度（激进重构/归一化/不做兼容/整体完善），缺少 3 个线上业务服务必备维度：

| 现有 4 维度 | 用户新 7 维度 | 差异 |
|:---:|:---:|------|
| ① 激进重构 | 1. 架构长远性 | 升级 — 强调 3-5 年扩展 + 清理技术债务 + 统一依赖版本 + 无循环依赖 |
| ② 归一化 | 2. 全局归一化 | 升级 — 强调 DB 表结构/字段定义/接口出入参/业务判断逻辑全项目统一 |
| ③ 不做兼容 | 3. 新旧兼容方案 | 明确 — 单人自用项目 = 不兼容旧系统，一次性切换 |
| ④ 整体完善 | 4. 现有业务完善 | 升级 — 强调补齐缺失业务流程 + 极端边界 + 全链路异常捕获 + 全分支覆盖 |
| — | 5. 性能资源优化 | **新增** — DB 慢查询/事务拆分/循环 IO/并发控制/连接池/内存 |
| — | 6. 安全合规加固 | **新增** — 权限校验/敏感数据脱敏/SQL 注入防护/操作审计日志 |
| — | 7. 长期维护成本 | **新增** — 架构/DB/接口文档 + 单元测试/回归测试 + 标准化注释 |

## 解决方案：升级 §2.0.5 为七维度评估

### 7 维度评估清单（完整定义）

#### 1. 架构长远性
- **目标**: 适配未来 3-5 年业务扩展，规范代码分层边界，清理历史技术债务
- **检查项**: 统一第三方依赖版本 / 剔除无用冗余包 / 无循环依赖 / 便于业务迭代扩容
- **与现有原则关系**: 升级 §2.0.5 ① 激进重构 + §2.0.4 N151 大修改架构视角

#### 2. 全局归一化
- **目标**: 统一项目编码规范、DB 表结构与字段定义、接口出入参返回格式、业务判断逻辑
- **检查项**: 消除重复实现 / 多套差异化处理逻辑 / 全项目规则收敛统一
- **与现有原则关系**: 升级 §2.0.5 ② 归一化

#### 3. 新旧兼容方案
- **目标**: 单人自用项目，新版完全不兼容旧系统，旧版本直接废弃下线
- **检查项**: 无需双跑/灰度/数据兼容过渡逻辑 / 一次性完成整体切换 / 规避存量兼容风险
- **与现有原则关系**: 明确 §2.0.5 ③ 不做兼容的应用场景

#### 4. 现有业务完善
- **目标**: 补齐原有缺失业务流程、各类极端边界场景，完善全链路异常捕获与容错处理
- **检查项**: 修复已知缺陷与 Bug / 覆盖全部业务分支
- **与现有原则关系**: 升级 §2.0.5 ④ 整体完善

#### 5. 性能资源优化
- **目标**: 针对性优化 DB 慢查询、事务拆分、循环 IO、并发控制逻辑，提升系统吞吐量
- **检查项**: 合理管控连接池/内存占用 / 解决现有运行性能瓶颈
- **适用场景**: GAF 有 DB 持久化 + 单人多 agent 客户端访问，适用但优先级中

#### 6. 安全合规加固
- **目标**: 统一接口权限校验、敏感数据脱敏处理，增加 SQL 注入防护
- **检查项**: 完善全链路操作审计日志 / 补齐数据访问/修改留痕能力 / 封堵安全漏洞
- **适用场景**: GAF 单人自用，优先级低；但权限校验 + SQL 注入防护仍需检查

#### 7. 长期维护成本
- **目标**: 配套完整架构、数据表、接口说明文档
- **检查项**: 补充单元测试/回归测试用例 / 标准化代码注释逻辑 / 大幅降低后续迭代/修改/接手维护成本
- **适用场景**: 所有修改场景必查

### 适用范围（用户补充说明）

1. **线上对外服务类后端程序**: 7 维度全部适用
2. **纯本地单机脚本**（无多用户访问/无 DB 持久化）: 可忽略「5. 性能资源优化」「6. 安全合规加固」
3. **GAF 项目定位**: PC 窗口控制 + 模拟器 + Django 后端 + 单人多 agent 客户端 → 7 维度全适用，5/6 优先级中/低

### 触发条件（任意一条即触发 7 维度评估）

- AI 准备修改代码（不限规模，小修改也适用）
- AI 准备修改规则文档（.trae/rules/ 或 docs/standards/）
- AI 准备修改 skill 文档（.trae/skills/*/SKILL.md）
- AI 倾向"最小改动"而忽略同根因问题
- 大修改场景（> 500 行 diff / 架构变更 / 跨模块 / DB 迁移 / API 契约变更）— 同时跑 N151 + 7 维度

### 与现有原则的关系（不重复定义）

| 现有原则 | 7 维度对应 | 关系 |
|---------|-----------|------|
| §2.0 三原则（扩展性/逻辑正确性/命名正确性） | 维度 1/2/7 | 7 维度是三原则的扩展版 |
| §2.0.4 N151 大修改架构视角 | 维度 1 | N151 限大修改场景，7 维度所有场景 |
| §2.0.5 修改四维度评估 | 维度 1/2/3/4 | **7 维度升级 §2.0.5**（4→7） |
| §3.7 L3-1 九维度扫描 | 维度 1/2/4/7 | L3-1 是评估扫描清单，7 维度是修改评估清单（互补） |
| §4.6 循环迭代反思 | 维度 4/7 | 反思时参考 7 维度 |

## 防错机制

- ❌ 只跑 4 维度评估（激进重构/归一化/不做兼容/整体完善）→ ✅ 跑 7 维度评估（补充性能/安全/维护成本）
- ❌ 代码修改时只考虑功能正确性 → ✅ 同时考虑性能/安全/维护成本
- ❌ 规则文档/skill 文档修改不跑评估 → ✅ 文档修改也跑 7 维度评估
- ❌ 大修改只跑 N151 → ✅ N151 + 7 维度同时跑
- ❌ 小修改跳过评估 → ✅ 小修改跑核心维度（1/2/3/4），大修改全跑 7 维度

## 评分纠偏（spec-37 教训, 2026-07-19 合并自 N167-architecture-long-term-priority.md）

### 症状
spec-37 L3 收尾的 docs/ vs .ai-memory/ 职责分配评估中, AI 自决选了"方案 A 最小修补" (只修 frontmatter 不修 .ai-memory/ 内部结构), 理由是"方案 B 中度重构需更新 5+ 处引用路径, 兼容成本高"。用户当场纠正: "ai 自决咋是按最小修改来的? 不是有 7 个维度吗? 最重要的是长期架构性啊?"

### 根因
1. **七维度评分错位**: 把"长期维护成本"维度误解为"迁移成本", 给方案 B 打 2/5 — 实际"长期维护成本"指 3-5 年长期受益, 一次性迁移成本应归到"新旧兼容"维度
2. **新旧兼容维度误判**: 给方案 B 打 2/5, 忽略了 §2.0.5 明确规定 "单人自用项目 = 不兼容旧系统, 一次性切换" — 应给 5/5
3. **架构长远性维度低估**: 给方案 A 打 4/5, 忽略了"只修 1/3 反模式, 另 2 类仍在"的事实 — 实际 3-5 年后还得重做, 应给 3/5
4. **违反 §2.0 三原则**: "改动范围由正确性决定, 不由'改动最小'决定" + "禁止'最小改动'自决方向"

### 评分修正规则
1. **维度 1 架构长远性优先**: 评分时第一个看, 3-5 年扩展性是核心判据
2. **维度 3 新旧兼容**: 单人项目 = 5/5 (不兼容旧系统, 一次性切换), 不因迁移成本扣分
3. **维度 7 长期维护成本**: 看 3-5 年长期受益, 不看一次性迁移成本 (一次性成本归维度 3)
4. **方案对比时**: 必须按 N151 5 步流程跑完, 不允许跳过 step_2 (识别反模式) 直接进 step_3 (A/B/C)

### AI 自决约束
- ❌ 禁止"最小改动"自决方向 (§2.0 三原则)
- ❌ 禁止把"迁移成本"误算入"长期维护成本"
- ❌ 禁止给单人项目"新旧兼容"维度打低分
- ✅ 七维度评分时, 维度 1 架构长远性 + 维度 7 长期维护成本双 5/5 才是理想方案
- ✅ 方案对比时, 优先选架构长远性更高的方案, 哪怕迁移成本略高

### 验证
spec-38 重新评分后方案 B 35/35, 领先方案 A 6 分 (架构长远性 +2, 长期维护成本 +2, 现有业务完善 +1, 全局归一化 +1)。用户批准方案 B。
