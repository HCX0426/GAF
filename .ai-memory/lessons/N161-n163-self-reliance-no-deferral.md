# N161 + N163 — 自决不推卸：架构决策 + 优先级排序 + 任务推进

## 家族合并说明

本文件合并 N161（架构决策不应推卸给用户 + 计划内任务不停下问继续）和 N163（优先级排序 + 任务推进自决）。两者同属"AI 自决不推卸"根因家族：
- **N161** 关注**架构决策不推卸**：AI 用 AskUserQuestion 让用户选 A/B/C 方案，违反 N151 大修改架构视角原则
- **N163** 关注**任务推进不推卸**：AI 列出优先级建议后问用户"要我处理 X 吗"，违反 N109/N127 自治原则

合并后形成完整的"自决不推卸"检查清单：从架构决策到优先级排序到任务推进，全部 AI 自决。

## N161: 架构决策不应推卸给用户 + 计划内任务不停下问继续

> **级别**: L1 可复用经验（Y/N 检查清单 + 影响 AI 全局行为）
> **分类**: AI 行为约束 — 自治边界 + 架构决策
> **来源**: 2026-07-14 用户反馈"这种继续的任务不需要让我输入继续，还有上面你让我做决定其实没必要，规则文档都说明方向了"
> **状态**: ✅ FIXED（本 lesson + 引用 N109/N127/N151）

### 触发原话

> "这种继续的任务不需要让我输入继续，还有上面你让我做决定其实没必要，规则文档都说明方向了，你觉得呢，需要沉淀吗"

### 症状

S4 阶段执行中，AI 出现 2 类反模式：

#### 反模式 1：计划内任务停下问"继续"
S4 commit + 验收完成后，AI 输出"建议新开对话推进 S5"，本质是停下等用户确认。违反：
- N109：计划内任务 AI 完全自治（spec 状态表 S5 ⏳ = 已计划任务）
- N113：完成后不停下问用户，立即推进
- N115：不问"是否开始"，完成立即推下一段
- N127：禁止"是否继续/下一步"类提问

#### 反模式 2：架构方案让用户选 A/B/C
S4 数据模型设计时，AI 用 AskUserQuestion 让用户选"方案 A (conversation_id 串联) / 方案 B (独立 QAMessage) / 方案 C (messages JSON)"，并问 on_delete 策略。违反：
- §2.0.4 N151：大修改架构视角原则 — AI 基于架构判定做决策，不推卸
- §2.0.5 ① 激进重构：选长期最优方案，不为短期便利留技术债
- §2.0.5 ② 归一化：消除重复概念，统一到单一来源
- §2.0 三原则：改动范围由正确性决定，不由"改动最小"决定

规则已提供完整判定标准（长期最优 + 归一化 + 不做兼容），AI 应直接决策"方案 B"，不需问用户。

### 根因分析

- **反模式 1 根因**：AI 将"上下文预算管理 N160"误用为停下理由。N160 第 4 条是"≥ 15 轮或上下文饱和时**主动提示**新开对话"，不是"停下等用户确认继续"。正确做法：直接推进 S5，仅在真正饱和时简短提示。
- **反模式 2 根因**：AI 将 AskUserQuestion 工具误用为"风险分散机制"——把架构决策推给用户，避免自己承担决策责任。但规则明确要求 AI 基于架构标准自决（N151 step 5「AI 自决约束」）。

### 修复方案

#### Y/N 检查清单（每次架构决策前必跑）

- [ ] 规则是否已提供判定标准？（归一化/激进重构/长期最优/不做兼容）→ 是 = AI 直接决策
- [ ] 是否所有备选方案都能用规则标准评估优劣？→ 是 = AI 直接决策
- [ ] 是否存在规则未覆盖的领域歧义（如用户业务偏好、外部约束）？→ 是 = 才用 AskUserQuestion
- [ ] AskUserQuestion 的选项是否都是"规则无法判定"的真歧义？→ 否 = 滥用

#### Y/N 检查清单（每次任务完成后必跑）

- [ ] 当前任务是 spec 状态表中的 ⏳/🔄 阶段？→ 是 = 已计划任务，立即推进下一段
- [ ] 是否已 commit + 验收通过？→ 是 = 立即推进，不停下
- [ ] 上下文是否真正饱和（工具输出堆积、轮次 ≥ 15）？→ 否 = 继续推进；是 = 简短提示后继续推进（不停下等确认）

#### AskUserQuestion 正当使用场景（仅以下 3 类）

1. **规则未覆盖的领域歧义**：如用户业务偏好（"QA 标题用中文还是英文"）、外部约束（"部署到哪个环境"）
2. **不可逆操作授权**：§3.5 三类（跨工作区/重写 history/不可逆删除）
3. **真正等价的方案选择**：规则标准无法区分优劣（罕见，如两个方案都符合归一化且长期最优）

#### AskUserQuestion 禁止使用场景

- ❌ 架构方案 A/B/C 选择（规则已给判定标准）
- ❌ on_delete 策略选择（CASCADE/SET_NULL/PROTECT 可用领域模型原则判定）
- ❌ 历史消息裁剪策略（可用 token 上限 + 用户体验判定）
- ❌ "是否继续/是否开始/下一步"（N127 明确禁止）

## N163: 优先级排序 + 任务推进自决

> **级别**: L1 可复用经验（Y/N 检查清单 + 影响 AI 全局行为）
> **分类**: AI 行为约束 — 自治边界（N161 姊妹篇）
> **来源**: 2026-07-14 用户反馈"这些优先级和排任务的顺序，你难道你处理不了吗？这种不需要问我吧？看一下要不要沉淀一下？"
> **状态**: ✅ FIXED（本 lesson + 立即应用）

### 触发原话

> "这些优先级和排任务的顺序，你难道你处理不了吗？这种不需要问我吧？看一下要不要沉淀一下？"

### 症状

审计完技术债务 + 测试缺口后，AI 列出"高/中/低优先级建议"，然后问用户"要我立即处理高优先级吗？还是先做别的？"

这违反了 N161（架构决策不推卸）+ N109/N113/N115/N127（自治家族）。优先级排序和任务推进顺序是 AI 自决范围：
- §3.6 N109：计划内任务 AI 完全自治
- §3.6 N113：完成后不停下问用户，立即推进
- §3.6 N115：不问"是否开始"
- N161：规则已给判定标准时 AI 直接决策

优先级排序的判定标准明确（P0>P1>P2>P3 + 依赖关系 + 改动量 + 风险），无需用户介入。

### 根因分析

AI 将"优先级建议"误用为"让用户拍板"的前置步骤，本质是推卸决策责任。但：
- 优先级标准已由 §4.8.1 定义（P0 紧急 > P1 重要 > P2 一般 > P3 低）
- 任务顺序由依赖关系 + 改动量决定（先小后大、先无依赖后有依赖）
- 这些都是 AI 能力范围内的技术判定

### 修复方案

#### Y/N 检查清单（每次想问"要我处理 X 吗"前必跑）

- [ ] 这是 spec 状态表中的 ⏳/🔄 任务？→ 是 = 立即推进，不问
- [ ] 这是技术债务 P0/P1？→ 是 = 立即处理，不问
- [ ] 这是规则已给判定标准的排序问题？→ 是 = AI 直接排序，不问
- [ ] 这是"是否开始/是否继续/先做哪个"？→ 是 = 禁止问（N127）

#### 优先级排序规则（AI 自决，不问用户）

1. **P0 紧急**：立即处理，阻塞其他工作
2. **P1 重要**：当前阶段内处理
3. **P2 一般**：当前阶段处理或登记 TD 待后续
4. **P3 低**：登记 TD，不阻塞当前工作
5. **同优先级**：按改动量升序（先小后大）+ 依赖关系（先无依赖后有依赖）
6. **快速修复 (< 10 行) 优先**：即使 P2/P3，如果 1-2 行能修，立即修不登记

#### 任务推进规则（AI 自决，不问用户）

- 审计/盘点完成后 → 按优先级排序 → 立即处理最高优先级 → 完成后立即推进下一项
- 禁止"列出建议让用户选"模式
- 禁止"要我处理 X 吗"提问
- 仅在 §3.5 三类 + N155 第四类需用户授权时才停下

#### AskUserQuestion 正当场景（N161 + N163 合并）

仅以下 3 类才用 AskUserQuestion：
1. **规则未覆盖的领域歧义**：用户业务偏好、外部约束
2. **不可逆操作授权**：§3.5 三类 + N155
3. **真正等价的方案选择**：规则标准无法区分优劣（罕见）

优先级排序、任务顺序、架构方案选择 — 全部 AI 自决。
