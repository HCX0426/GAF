## 1. 症状 (本轮 OCR bug 排查的具体表现)

BD2 chain 执行失败, OCR 节点报 "No image available in context for OCR"。排查过程:

| 阶段 | AI 反应 | 用户提示 | 暴露的思维链缺陷 |
|------|---------|---------|-----------------|
| 第 1 反应 | 直接定位 `ocr.py` `_get_image` 缺 fallback, 准备写测试修复 | (无) | **先动手后系统评估** — 未先评估链路归一化 |
| 第 2 反应 | 扩展到评估"截图→识别→点击"链路的归一化情况, 输出 4 种截图获取策略表格 | "你的意思是从截图到识别,到点击,这些步骤没有归一化?评估这些过程" | **单点思维** — 只看 fail 节点, 不看链路 |
| 第 3 反应 | 扩展到 AI 思维链/工作流/规则文档三维评估, 调研三维度规则覆盖度, 输出 12 项缺失规则清单 | "规则文档没说要从哪些维度上看嘛,还是ai的思维链有问题?我需要你再次评估ai思维链,工作流,规则文档,然后再看这些问题,错误一定不能被隐藏了,一定要有日志" | **代码层根因优先** — 未意识到代码 bug 背后是规则盲区/工作流缺陷/思维链问题 |

AI 默认走"最短路径" (直接定位 fail 节点 + 写测试修复), 缺少"先评估链路归一化 + 三维根因"的思维链检查点。经用户三次提示才完成完整评估。

## 4. 验证 (下次 bug 排查时 AI 主动跑三维评估)

下次 bug 排查时, AI 应主动 (无须用户提示) 跑以下思维链检查点:

```
[bug 排查启动阶段]
1. fail 节点上下游链路归一化评估 (N182)
   - fail 节点上下游节点是否归一化?
   - fail 节点是否是同根因家族的唯一例外?
2. 三维根因评估 (N183)
   - 代码层根因: 具体代码 bug
   - 工作流层根因: 测试覆盖盲区 / e2e 时机缺陷 / 隐式契约
   - 规则层根因: 规则盲区
3. 节点观测性检查 (N184)
   - fail_result 是否带 logger.warning + exc_info?
   - 错误消息是否包含上下游上下文?
4. 测试覆盖盲区反思 (N185)
   - 为什么测试没覆盖到?
   - 同类关键方法是否同步补单测?
```

若 AI 默认走"最短路径" (直接定位 fail 节点 + 写测试修复) 而未跑上述检查点, 即触发本 lesson 反模式。

## 3. 修复方案 (TD 模板新增三维根因评估必填字段)

### 3.1 TD 模板新增"三维根因评估"必填字段

TD 条目模板新增必填字段, 与 N174 "修复方案验证"字段互补:

- **代码层根因**: 具体代码 bug (如 `_get_image` 缺 device fallback)
- **工作流层根因**: 测试覆盖盲区 / e2e 时机缺陷 / 隐式契约未文档化
- **规则层根因**: 规则盲区 (如 agent 节点测试规则缺失)

### 3.2 commit 前三维根因评估流程

bug 修复 commit 前必跑三维根因评估:

```
[bug 修复 commit 前]
1. 代码层根因: 具体代码 bug 是什么? 同根因家族是否覆盖?
2. 工作流层根因: 测试覆盖盲区在哪? e2e 时机缺陷? 隐式契约未文档化?
3. 规则层根因: 规则盲区在哪? 哪条规则缺失?
4. TD 登记三维根因字段是否填全?
```

### 3.3 与 N174 互补关系

- **N174** (修复方案验证): 验证修复方案是否覆盖代码层 grep 扫描 (事后验证)

# N184 — 节点观测性硬约束

> **家族**: 并入 N182-N185 家族 (同一 OCR bug 事件, 2026-07-22)
> **L1 分级**: L1-大 (节点观测性规则缺失, 5 层分发: lesson + rules + handbook + yn-matrices + failure-modes)

## 1. 症状 (OCR 节点 fail_result 缺上下游上下文)

OCR 节点 `_get_image` 返回 None 时, `execute()` 抛出错误信息 "No image available in context for OCR", 该消息不含任何上下游上下文:

| 缺失信息 | 具体表现 | 用户排查代价 |
|---------|---------|------------|
| 上游 screenshot 节点是否执行 | 错误消息不含 screenshot 节点执行状态 | 用户需翻 jsonl 日志确认上游是否跑 |
| context 里有哪些变量 | 错误消息不含 context 键列表 | 用户需加 debug 打印才能知道 context 内容 |
| device.capture_screen 是否尝试 | 错误消息不含 device fallback 尝试记录 | 用户需读源码才知道有 fallback 路径 |
| 失败原因 | 错误消息只说"No image", 不说为什么没有 | 用户需逐步排查整个链路 |

AI 默认接受简短错误消息, 未意识到节点 fail_result 必须带上下游上下文。用户原话: **"错误一定不能被隐藏了, 一定要有日志"**。

## 2. 根因 (节点层无观测性硬约束规则)

现有规则体系在 agent 节点层无观测性硬约束:

| 已有规则 | 范围盲区 | 本轮 OCR 节点 fail 的具体表现 |
|---------|---------|---------------------------|
| **project_rules** | 无节点观测性硬约束章节 | 节点 fail_result 只抛简短错误消息, 不带上下游上下文 |
| **N182** (链路归一化) | 评估 fail 节点上下游链路归一化, 未约束 fail 信息完整性 | AI 评估了链路归一化, 未评估 fail 消息是否带上下文 |
| **N150** (整体框架看问题) | 覆盖"同类问题在其他文件", 未覆盖"节点观测性" | AI 未评估其他节点是否同样缺观测性 |
| **logger 使用规范** | 无统一规则要求 fail 路径必用 logger.warning + exc_info | 现有节点 fail_result 只 raise, 不 logger.warning |

**根本缺陷**: agent 节点层无观测性硬约束规则。现有节点 fail_result 只抛简短错误消息, 不带上下游上下文。logger.warning 未在 fail 路径统一使用, except Exception 可能静默吞错 (pass)。

## 3. 修复方案 (节点 fail_result 观测性硬约束)

### 3.1 fail_result 必带的三要素

节点 fail_result 必带:

1. **logger.warning + exc_info=True**: 失败路径必须记录日志, 含异常堆栈
2. **错误消息含上下游上下文**:
   - 输入参数 (如 context 键列表)
   - 上游节点状态 (如 screenshot 节点是否执行 / 产出格式)
   - 失败原因 (如 device.capture_screen 是否尝试 / 失败原因)
3. **禁止静默吞错**: `except Exception` 必须 `logger.warning`, 不能 `pass`

### 3.2 示例 (OCR `_get_image` fail 改造)

改造前:
```python
raise RuntimeError("No image available in context for OCR")
```

改造后:
```python
logger.warning(
    "OCR _get_image failed: context_keys=%s, screenshot_executed=%s, "
    "device_capture_attempted=%s, reason=%s",
    list(context.keys()),
    context.get("_screenshot_executed", "unknown"),
    device_capture_attempted,
    reason,
    exc_info=True,
)
raise RuntimeError(f"No image available in context for OCR: {reason}")
```

### 3.3 通用约束 (所有 agent 节点)

- 所有节点 fail_result 必带 logger.warning + exc_info
- 错误消息必含上下游上下文
- except Exception 禁止 pass, 必须 logger.warning

## 4. Y/N 检查矩阵 (节点观测性硬约束)

| # | Y/N 检查项 | 期望 |
|---|-----------|------|
| 1 | fail_result 是否带 logger.warning + exc_info? | Y |
| 2 | 错误消息是否包含上下游上下文 (输入参数 + 上游节点状态 + 失败原因)? | Y |
| 3 | except Exception 是否都有 logger.warning (禁止 pass)? | Y |
| 4 | fail 路径是否禁止 return None 不抛错 (静默失败)? | Y |
| 5 | 节点观测性是否在 code review 检查清单? | Y |

若任一项为 N, 即触发本 lesson 反模式 — 节点 fail_result 缺观测性, 错误被隐藏。

## 5. 与现有规则关系

| N## | 已有规则 | 范围盲区 | 本 lesson 补全 |
|-----|---------|---------|---------------|
| N182 | 链路归一化评估 (fail 节点上下游) | 评估链路归一化, 未约束 fail 信息完整性 | N184 观测性 (fail 信息完整性) |
| N150 | 整体框架看问题 (同类问题在其他文件) | 未覆盖节点观测性 | N184 节点观测性硬约束 |
| N183 | 三维根因评估 (commit 前) | 评估三维根因, 未约束 fail 观测性 | N184 fail_result 观测性 |

**互补关系**: N182 链路归一化 (fail 节点上下游归一化) + N184 观测性 (fail 信息完整性) + N150 整体框架 (同类节点同步检查)

# N185 — 测试覆盖盲区 = AI 思维链缺陷

> **家族**: 并入 N182-N185 家族 (同一 OCR bug 事件, 2026-07-22)
> **L1 分级**: L1-大 (测试覆盖盲区元层反思缺失, 5 层分发: lesson + rules + handbook + yn-matrices + failure-modes)

## 1. 症状 (OCR `_get_image` 无单测覆盖, AI 未反思为什么)

OCR `_get_image` 方法无单测覆盖 (48 tests 里无 `_get_image` 直接测试)。AI 第一反应"写测试修复", 未反思"为什么 48 tests 没覆盖到这个关键方法":

| 可能原因 | 具体表现 | AI 是否反思 |
|---------|---------|-----------|
| 测试用例缺失 | 48 tests 里无 `_get_image` 直接测试 | 否 — AI 直接准备补单测, 未问"为什么没测" |
| 测试场景设计缺陷 | 无 fallback 路径测试 (device.capture_screen fallback 未覆盖) | 否 — AI 未评估测试场景设计是否完整 |
| AI 思维链缺陷 | 未意识到节点关键方法必须有非 happy path 单测 | 否 — AI 未反思思维链本身的盲区 |

AI 默认走"写测试修复" (补 `_get_image` 单测), 缺少"测试覆盖盲区 = AI 思维链缺陷"的元层反思。**是测试用例缺失 (补单测), 还是测试场景设计缺陷 (没覆盖 fallback 路径), 还是 AI 思维链缺陷 (没意识到节点关键方法必须有非 happy path 单测)?** — AI 未区分这三种原因。

## 2. 根因 (N156 范围盲区 + testing-conventions 留白)

现有规则体系在测试覆盖盲区反思场景有范围盲区:

| 已有规则 | 范围盲区 | 本轮 OCR `_get_image` 无单测的具体表现 |
|---------|---------|---------------------------|
| **N156** (测试先于理解) | 限"测试场景端点确认", 未抽象到元层"测试覆盖盲区 = AI 思维链缺陷" | AI 准备写测试, 未反思"为什么测试没覆盖到 `_get_image`" |
| **testing-conventions.md** | 三层表无 agent 节点测试层, agent 节点关键方法无强制单测要求 | 48 tests 无 `_get_image` 单测, testing-conventions 未要求 agent 节点关键方法必须有单测 |
| **N167** (§2.0.5 七维度评估) | 维度 5 (测试覆盖) 限"修复后补测试", 未要求"修复前反思盲区" | AI 准备写测试修复, 未先反思测试覆盖盲区 |
| **N182** (bug 排查链路归一化) | 评估链路归一化, 未评估测试覆盖盲区 | AI 评估了链路, 未评估测试覆盖盲区 |

**根本缺陷**: N156 (测试先于理解) 限"测试场景端点确认", 未抽象到元层"测试覆盖盲区 = AI 思维链缺陷"。testing-conventions.md 三层表无 agent 节点测试层, agent 节点关键方法无强制单测要求。AI 准备写测试修复时, 默认走"补单测"而不反思"为什么没测"。

## 3. 修复方案 (测试覆盖盲区反思 + testing-conventions 扩层)

### 3.1 AI 准备写测试修复前必跑"测试覆盖盲区反思"

AI 准备写测试修复前必跑以下反思:

```
[测试覆盖盲区反思]
1. 为什么测试没覆盖到?
   - 测试用例缺失? (补单测)
   - 测试场景设计缺陷? (没覆盖 fallback / 非 happy path)
   - AI 思维链缺陷? (没意识到关键方法必须有单测)
2. 同类关键方法是否同步补单测?
3. testing-conventions 是否覆盖 agent 节点层?
4. 节点关键方法是否有非 happy path 单测?
```

### 3.2 testing-conventions 三层表扩四层

testing-conventions.md §1 三层表 (unit / integration / e2e) 扩为四层:

- 第 1 层: unit (原有)
- 第 2 层: integration (原有)
- 第 3 层: e2e (原有)
- **第 4 层: agent 节点测试** (新增)
  - 节点关键方法必须有单测 (含非 happy path)
  - fail_result 路径必须有单测
  - fallback 路径必须有单测

### 3.3 通用约束 (所有 agent 节点关键方法)

- 节点关键方法必须有非 happy path 单测
- 测试覆盖盲区反思在写测试前而非后
- 同类关键方法同步补单测 (不只看当前 fail 方法)

## 4. Y/N 检查矩阵 (测试覆盖盲区反思)

| # | Y/N 检查项 | 期望 |
|---|-----------|------|
| 1 | 测试覆盖盲区是否归因到 AI 思维链层 (而非只补单测)? | Y |

| 3 | testing-conventions 是否覆盖 agent 节点层 (四层表)? | Y |
| 4 | 节点关键方法是否有非 happy path 单测 (含 fallback / fail_result)? | Y |
| 5 | 测试覆盖盲区反思是否在写测试前而非后? | Y |

若任一项为 N, 即触发本 lesson 反模式 — 测试覆盖盲区未归因到 AI 思维链层, AI 只补单测不反思。
