### N167 动态权重表 v1 (2026-08-27 用户决策 D)

> **用户指令**: "等权打分 + 判据优先级，我需要自己评估这七个维度是否要加权" → 选型 D（按任务类型动态权重）。

| 任务类型 | 重点维度（必评 + 必填理由） | 标准维度 | 豁免维度（记基线 3，不填理由标 `N/A→3`） | 自决额外门槛 |

| **security / 安全加固** | 6 | 1, 4 | 2, 3, 5, 7 | 同上 |
| **doc / 文档·规则·skill 修改** | 1, 4 | 7 | 2, 3, 5, 6 | 同上 |

**执行规则**:
1. 评分前先按决策树 task_type 查表确定权重档位（被调用的评估即本表判据）
2. **重点维度**: 必须逐维评分且必填一行实质理由（spec-49 ⑤⑥ 理由要求扩展到全部重点维度），任一 <4 分 → 禁止自决
3. **豁免维度**: 视为"此任务类型下噪声"，记基线 3 分，评分表标注 `N/A→3`，不强制理由
4. 总分口径不变（7 维各 5 分 = 满分 35，豁免 3 分计入），自决门槛维持 ≥19 且领先 ≥5；重点维度否决门槛为补充前提
5. 与现有三修正兼容：维度 3 单人项目一律 5/5；维度 1 首要判据；维度 7 看长期受益
6. 上一节"维度适用场景（按修改类型）"的必跑/可选维度与本表冲突时，**以本表为准**（动态权重 v1 取代静态必跑集）

### N178 AI 思维链纠偏硬约束 (spec-59-A 强化 — 防 AI 既是规则制定者又是评分者; spec-59-B 从 rules §2.0.5 迁入)

> **来源**: spec-59-A 元评估 — AI 思维链 4 项弱项 (反向论证循环论证 / 评分合理化 / 过度治理 / 范围扩张)
> **核心反模式**: AI 既是规则制定者又是执行者又是评分者 → 利益冲突 → 倾向给自己高分、扩大范围、形式化反思

- ✅ **N178-A1 反向论证禁循环论证**: 反向论证不得用 "AI 自定的规则" 排除方案 (例: "方案 B 违反原 spec 拆 spec 计划" — 但拆 spec 计划本身是 AI 自定 → 循环论证)。必须用**外部约束**排除 (例: 性能基线 / 用户明确诉求 / 安全风险)
- ✅ **N178-A2 评分维度 4-7 必填实质理由**: 维度 4 业务完善 / 5 性能 / 6 安全 / 7 长期维护 不允许默认 5/5, 必填一行 "为何打此分" 实质理由 (防 AI 模式化打 5/5 凑分)。例: "维度 4 = 4/5 因 5 项核心 6 项留 spec-59-B/C, 业务完善未全覆盖"
- ✅ **N178-A3 过度治理检查**: 修复前必问 "单步写加 atomic / 单字段加索引 的价值是否 > 改动成本?"。例: ChangePassword 单步 user.save + log_audit 加 atomic 价值低 (log_audit 失败不该回滚 user.save), 应 KEEP
- ✅ **N189 增强 N178-A3**: 治理体系评估时, 必先区分 "AI 主导开发必需的治理" vs "治理形式化"; 判定标准是 **执行率 + evidence**, 不是文件数量. 数量多 (66 lessons + 9 yn-matrices) ≠ 过度治理; 执行率 0% (N173 用时测量) + 无 evidence = 过度治理. AI 主导开发模式治理复杂度 ≈ AI agent 框架复杂度, 是内在需求. 详见 lesson N189
- ✅ **N178-A4 spec 范围限制**: spec 实际改动不得超 TD 描述范围 30% (例: TD 描述 9 处 RBAC → spec 实际改不得超 12 处)。超出 30% 必须在 spec 文件 "范围偏差" 段说明理由 + 用户确认
- ❌ **禁止** 反向论证用 AI 自定规则排除方案 (反模式: spec-58-A 排除方案 B "违反原 TD-296 拆 spec 计划", 但拆 spec 是 AI 自定)
- ❌ **禁止** 评分维度 4-7 无理由打 5/5 (反模式: spec-57 A=35/35 满分, 但 7 处 KEEP 是合理决策, 维度 4 业务完善不该满分)
- ❌ **禁止** 过度治理 (反模式: spec-58-A A3 ChangePassword 单步写加 atomic 价值低)
- ❌ **禁止** spec 范围超 TD 描述 30% 无说明 (反模式: TD-295 描述 9 处 RBAC → spec-57 实际扫描 17 处 → 改 10 处, 超 11% 但未说明)

### §1.1 跨 app import 解耦模式适用范围 (spec-41 TD-277 + spec-59-E N178-A3 调整)

> **来源**: spec-59-E Phase 6 N180 元评估弱项 2 — spec-41 TD-277 模式描述只说 "跨 app import 迁 service 层", 未明确使用次数阈值, 导致 spec-59-E Phase 2 中 gaf_ai (4 处使用 → service 层) 与 executions (35 处使用 → apps.get_model) 模式不一致, 决策合理但模式适用范围未沉淀成规则.
> **闭环**: spec-59-F (N180-C5 A 立即修, 小修改 < 50 行规则文档补充)

**判定条件** (按跨 app model 使用次数选模式):

| 跨 app model 使用次数 | 推荐模式 | 理由 | 示例 |
|:---:|---|---|---|
| **≤ 5 处** | **service 层** (1:1 函数映射, spec-41 TD-277 严格模式) | 函数少, 1:1 映射清晰, view 层不直接依赖 model | spec-41 TD-277: accounts/views.py 4 处使用 agents.models → agents/services.py 4 函数; spec-59-E: gaf_ai 4 处使用 → gaf_ai/services.py 4 函数 |
| **≥ 10 处** | **apps.get_model module-level 赋值** (lazy, 避免 8+ 函数过度治理) | service 层需 8+ wrapper 函数, 过度治理 (N178-A3); apps.get_model 消除顶层 import 同时保持 name lookup 简洁 | spec-59-E: executions/views.py 35 处使用 tasks.models → `TaskExecution = apps.get_model('tasks', 'TaskExecution')` module-level |
| **5-10 处之间** | **case-by-case** (N178-A3 评估) | 边界场景, 按 N178-A3 评估: service 函数是否 1:1 映射? view 是否是 model 的视图层 (无自己的 models)? | N/A (spec-59-E 未触发) |

**N178-A3 评估要点** (5-10 处之间或边界场景):
- service 函数是否 1:1 映射? (若 1 个 model 操作对应 1 个 service 函数, service 层合理; 若 1 个 model 操作需 2+ service 函数, apps.get_model 更合适)
- view 是否是 model 的视图层 (无自己的 models)? (若是, apps.get_model 更合适; 若不是, service 层更合适)
- 改动成本 vs 收益? (service 层改动成本高但解耦更彻底; apps.get_model 改动成本低但仍有 module-level 依赖)

**硬约束**:
- ✅ 跨 app import 解耦必跑 N178-A3 评估 (即使 ≤ 5 处或 ≥ 10 处, 也要记录评估理由)
- ✅ service 层函数命名: `get_<model>_for_<scope>` / `get_<model>_qs_for_<scope>` / `count_<model>_since` (spec-41 TD-277 模式)
- ✅ apps.get_model 赋值必须在 module-level (非函数内), 注释说明 "spec-XX / TD-NNN: avoid top-level cross-app import" + N178-A3 评估理由
- ❌ **禁止** 跨 app import 解耦时不跑 N178-A3 评估 (反模式: spec-59-E Phase 2 executions 部分未评估直接迁 service 层 → 8+ 函数过度治理)
- ❌ **禁止** apps.get_model 在函数内调用 (性能差, 每次 view 调用都查 apps registry)

## §2 backup/restore 对称检查矩阵

### N168 backup/restore 对称检查 Y/N 矩阵 (新增 — 修改时安全维度)

> **来源**: L3-1 ③ 架构层扫描发现 `backend/tasks/backup_views.py` P0 安全漏洞
> **触发**: 新增/修改任何备份/恢复/导入/导出功能时必跑

### Y/N 检查清单

| # | 检查项 | Y/N | 反模式 (N) | 正确做法 (Y) |
|:---:|------|:---:|------|------|
| 1 | create/restore 是否用对称 API? | Y | create 用 dumpdata, restore 用 cursor.execute (不对称) | create 用 dumpdata ↔ restore 用 loaddata (Django 对称管理命令) |
| 2 | 文件名是否与内容格式一致? | Y | 文件名 .sql 但内容是 JSON | 文件名 .json 对应 JSON fixture |
| 3 | restore 路径是否有 round-trip 单测? | Y | restore 从未测试 (长期累积为 P0 漏洞) | 至少 1 个 create→restore round-trip 测试 |
| 4 | 是否有恶意输入拒绝测试? | Y | 无 | 上传恶意 SQL/超长/非 ZIP 内容, 验证被拒绝而非执行 |
| 5 | 是否执行用户上传内容? | N | cursor.execute(f.read()) | 用 Django 管理 command (loaddata) 解析, 不直接执行 |
| 6 | 是否有源码回归守卫? | Y | 无 | grep 验证生产代码无 cursor.execute + 无错误文件名 |
| 7 | 异常路径是否返回正确状态码? | Y | 异常静默吞或 200 | 异常返回 500 + 日志, 输入校验失败返回 400 |

### 反模式扫描 grep 命令

```bash
# 扫描 backup/restore 类文件中的危险模式
grep -nE "cursor\.execute\(.*f\.read" backend/  # 执行用户上传内容
grep -nE "database\.(sql|json)" backend/         # 文件名检查
grep -rn "call_command\('dumpdata'" backend/     # 必须配对 call_command('loaddata')
```
