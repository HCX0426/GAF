## 一、问题根因

### TD-314: `-n auto` 16 workers MemoryError
- **症状**: `pytest backend/ -n auto` → 1952 passed, **3 failed** (MemoryError) on screenshot tests
- **根因**: pytest-xdist `-n auto` 按 CPU 核数 (本机 16) 启动 16 workers 并行, 跑截图清理测试时内存峰值超 Windows 进程限制
- **影响**: N177 全套测试无法在并行模式下跑通, 阻塞循环模式每 2 spec 全套验证节奏

### TD-300 延伸 N+1 治理 (spec-69 遗漏)
- spec-69 审计 subagent 报告 22 处 NEEDS_SELECT_RELATED, 实际 Edit 时发现 20 处已存在
- **遗漏**: 9 个 views.py 中仍有 select_related/prefetch_related 缺失, spec-69 commit 时未一并修复
- **修复**: 9 个 views.py 补充 select_related/prefetch_related (accounts/executions/gamestate/metrics/pipeline/plugins/qa/resources/scheduler)

## 二、修复方案

### 方案 A: `-n auto` → `-n 8` (固定 8 workers) ✅ 采用
- 改 project_rules.md §4.9 (2 处) + tech-stack.md §9.2 (3 处) `-n auto` → `-n 8`
- 8 workers 内存可控 (Windows 进程内存限制内), 4-4.5x 加速 (vs 单核)
- 验证: `pytest backend/ -n 8 -q` → **1955 passed, 3 warnings in 197.60s** ✅ 0 failed

### 方案 B: `-n 4` (更保守) — 未采用
- 内存更安全, 但 4 workers 加速仅 2-2.5x, 大修改全套验证耗时过长
- 权衡: 8 workers 已实测稳定 (197s), 4 workers 过度保守

### 方案 C: `-n auto --max-worker-restart=0` — 未采用
- 仍是 16 workers, MemoryError 根因未解决, 只是抑制 worker 重启
- 治标不治本, 不符合 §3.3 根因修复原则

### TD-300 延伸治理 (与 TD-314 一并 commit)
- 9 个 views.py 补充 select_related / prefetch_related (具体见 commit diff)
- 与 spec-69 同源 (TD-300 N+1), 一并 commit 减少 spec 粒度碎片
